## 两种强制签名构建

工程固定 electron-builder 26.15.3，使用其 v26 `win.signtoolOptions` / `win.azureSignOptions` 接口；[v26 文档](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/)。不能照搬 v27 的 `win.sign` 配置。

证书方式需要构建环境中配置以下字段：

- `GEMS_SIGNING_MODE=certificate`
- `GEMS_PUBLISHER_NAME`：证书发布者的 Common Name（必须精确匹配）。
- `CSC_LINK` 或 `WIN_CSC_LINK`：合法取得的证书，由私密构建配置提供。
- `CSC_KEY_PASSWORD` 或 `WIN_CSC_KEY_PASSWORD`：证书密码，不能写入源码或发到聊天中。

Azure 方式需要：

- `GEMS_SIGNING_MODE=azure` 和 `GEMS_PUBLISHER_NAME`
- `GEMS_AZURE_SIGNING_ENDPOINT`：签名账户所在区域的官方 HTTPS 根地址。
- `GEMS_AZURE_SIGNING_ACCOUNT` 和 `GEMS_AZURE_CERTIFICATE_PROFILE`
- `AZURE_TENANT_ID`、`AZURE_CLIENT_ID`、`AZURE_CLIENT_SECRET`：有权签署该证书配置的服务身份，放在秘密配置中。

目前 Azure 只支持显式服务主体环境凭据，不自动登录、不创建账户或扩大权限。此接口通过实际 builder schema 校验，尚未在真实 Azure 账户上签名。

配置就绪后：

```powershell
npm run signing:preflight
npm run dist:signed
npm run test:ui
$env:GEMS_REQUIRE_SIGNATURES = '1'
./tests/install.ps1
node tests/portable.mjs
npm run source
node scripts/release-manifest.mjs --require-signed
```

预检只检查配置字段，不声称证书有效。构建使用 `forceCodeSigning=true`，缺少签名不能降级输出未签名发行包。后检通过 Windows 的只读 Authenticode 命令验证桌面程序、安装器、便携包；要求可信状态 Valid、发布者一致、代码签名用途、非自签名、时间戳和证书指纹。安装测试另外验证实际安装的程序和卸载器。任一失败都没有“可发行”结论。

GitHub Windows 流程手动运行时，选择 `signed_preview=true` 与签名方式。发布者与 Azure 配置信息放入同名 repository variables；PFX 放入 `GEMS_CODE_SIGNING_CERTIFICATE`，密码放入 `GEMS_CODE_SIGNING_PASSWORD`，Azure 凭据放入同名 secrets。默认 push 构建仍是开发包。流程只上传构建附件，不自动发布到互联网；本轮未在远程执行。

`artifacts/signed-preview-signatures.json` 仅在实际签名检查通过时生成，包含程序 SHA-256 与公开证书指纹。`manifest.json` 始终保留 `fullRequirementsPassed=false` 和 `commercialReady=false`，直到功能与商业授权终验有证据。源码归档排除常见私钥、环境凭据、构建缓存与未知根文件，发布前仍要人工核对实际附件内容。
